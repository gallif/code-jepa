Code-JEPA 0.5B · Benchmark report · 15 Nov 2026

What did JEPA training buy us, and what did it cost?

We fine-tuned Qwen2.5-Coder-0.5B so that every block, function and whole program gets a vector that matches its plain-English description. This page walks through where those vectors beat the model we started from, where they don't, and how much the language model degraded along the way.

Setup

What was compared, and how

All four models share the Qwen2.5-Coder-0.5B architecture. Two are Code-JEPA releases, and two are controls that isolate what the JEPA objective adds.

free

Code-JEPA. Program-level tokens read all code tokens directly.

tree

Code-JEPA. Program-level tokens read only the function tokens, so each level is built from the one below.

E1

Same training data, next-token loss only. Isolates the effect of the alignment objective.

E0

Qwen2.5-Coder-0.5B as released. The starting point.

How Code-JEPA reads a program

Each tree node gets a special token that sees only its own span (steps, units) or its children. Its vector is trained to match an LLM-written description of that node. No descriptions are needed at inference.

free vs tree: in tree, intent/approach see only the unit tokens. In free, they see every code token. Steps and units are identical in both.

01

Matching code by algorithm

The question: if two programs solve the same problem in different ways, do their program vectors land near each other? Measured on 8,000 TACO programs (4,000 problems, 2 solutions each), zero-shot cosine on centred vectors.

free roughly doubles same-problem retrieval over the base model. Note that tree collapses here (.07). Its program tokens work in-domain but barely transfer to TACO.

Probes for algorithm tags and complexity class show free ≈ E0. The base model already "knows" which algorithm family a program uses. JEPA mainly makes that information directly usable as a nearest-neighbour signal.

02

Pointing to the location in the code

The question: given a description of one block or function, can the model pick out which block or function it describes? Candidates are the blocks or functions of the same program (or of the edited files, for SWE-bench).

Within a single program, both JEPA variants are excellent: ~.86 R@1 vs .43–.71 for the controls, well above chance. This is the clearest win in the report.

But it doesn't transfer to real repositories.On SWE-bench Lite (issue → edited function, 272 issues) every model, including E0, scores .15. That's above chance (.06) but far below simple BM25 (.32) and gte-modernbert (.39).
Caveat that favours usThe in-program descriptions are LLM-written in the training style. E0/E1 use a ridge probe trained on other TACO problems. Ours are zero-shot in the shared 256-d space (or a ridge probe on raw vectors).

03

Robustness to renaming and reformatting

The question: does the representation track behaviour or surface form? We built 703 test-checked variants: renamed and reformatted copies that still pass, and one-token mutants that fail.

Renamed correct copy closer than a broken mutant
3% free · 0% E0
Reformatted correct copy closer than a broken mutant
28% free · 14% E0

Changing every name moves the vector far more than a bug that breaks the program. Both models still notice where the bug is: the most-moved step is the mutated one 91% (free) / 88% (E0) of the time, vs 20% chance.

AdvTest: what happens when identifiers are anonymised

6,000 functions, docstring → function, MRR. Identifiers replaced with Func / arg_i.

Our models lose 75–85% of their score when names are removed. The dedicated embedders lose ~35%. Right now, much of what our vectors encode is identifier names, not semantics.

04

One model for text and code, vs dedicated embedders

The question: can the shared code/description space replace a dedicated text ↔ code retriever? MRR.

free beats E0 and UniXcoder on problem-to-solution search. However, gte-modernbert, a general embedding model, wins every row by a wide margin. tree is near zero on problem statements, the same transfer failure seen in §1.

jina-code and CodeRankEmbed weren't tested because they need trust_remote_code.

05

Language-model drift vs the original model

The question: Code-JEPA shares its backbone with a language model. Did the alignment objective damage it? Teacher-forced perplexity on the same tokens, plus KL from E0 (nats/token).

The key comparison is JEPA vs E1, since both saw the same data. tree has the lowest KL on every corpus, and free is at or below E1 everywhere except WikiText (.284 vs .283). The alignment objective adds no drift.

The ~30% perplexity increase on general Python (CodeSearchNet 5.6 → 7.4) and English (WikiText 12.8 → 17) comes from fine-tuning on CodeContests. E1 shows it too.

06

Code generation

The question: does the model still write code? Greedy pass@1 (%).

On standard benchmarks the base model wins almost everywhere. The fine-tunes win only on in-domain CodeContests, especially with the training-style prompt. Among the fine-tunes, JEPA ≈ E1, which again shows that the cost comes from the data, not the objective.

Why MBPP drops (and why it looks fixable)Fine-tuned models often ignore the function name the test requires: 60–87 of 378 MBPP outputs use the wrong name, vs 17 for E0. That's a side effect of training only on stdin/stdout CodeContests programs.

Caveats

What to keep in mind

  • One seed per model. Seeds 23 and 37 exist and can be exported and added.
  • The rename-vs-mutant test pits renaming every identifier against changing one token, which is deliberately hard. Reformatting is the gentler version.
  • AdvTest uses 6,000 of the 9,826 test functions, the ones that could be matched to their original source.
  • LiveCodeBench wasn't run. Its private tests are pickled, and loading them would execute downloaded code.
  • Training data is competitive programming only. Production-style code (multi-file, long identifiers, libraries) is out of distribution, which is likely part of why SWE-bench is flat.
