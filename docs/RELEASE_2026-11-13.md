# Code-JEPA 0.5B — hierarchical code features (release 2026-11-13)

Two pretrained encoders that give a vector for **every step, function (unit), and the whole program** of a Python
program. Both are Qwen2.5-Coder-0.5B fine-tuned with Code-JEPA on CodeContests (11,448 programs, 4 epochs, seed 82).

| Folder | Variant | Approach / intent tokens read… |
|---|---|---|
| `code-jepa-0.5b-tree-s82/` | **tree** (the method's default) | only the unit (function) tokens: each level is built from the level below |
| `code-jepa-0.5b-free-s82/` | **free program tokens** (alternative) | all code tokens directly; steps and units still use the tree |

In both, steps and units are tied to their own lines of code. The free variant is better at every level in our tests.
The tree variant is the one whose program level is built from the functions.

## What you get per node

| Level | Node | What the vector encodes (trained to match) |
|---|---|---|
| `step` | one block of code (tree-sitter block, nested at most 2 deep) | its one-line pseudocode description |
| `unit` | a function / method / class / `main` | its responsibility + contract |
| `approach` | the whole program | how it works: strategy, data structures, complexity |
| `intent` | the whole program | what task it solves |

For each node: `node_id`, `level`, `span` (1-based line range), `parent_id`, and two vectors:
- `raw`: the model's last-layer state at the node's token (float32[896]). **Recommended for downstream use.** In our
  linear probes it carries the most information.
- `head`: the level's 256-d projection, i.e. the space where code and descriptions were aligned. Use it to compare
  code with *descriptions* encoded by the same model (`with_text=True`).

No descriptions are needed at inference; the code view never sees them. You do need the tree (steps / units with
line spans), in the same JSONL schema as the training data (`L4_code`, `L2_units` with `steps` / `methods` and
`span`). The tree-sitter pipeline that produced the dataset can produce it for new code.

## How good are the features (CodeContests validation, 98 programs)

Linear-probe retrieval: map a level's description to its code vector and find the right node among all validation
nodes of that level. R@1 is the fraction found first; chance is about 1% for approach/intent and 0.2% for steps.
Mean of three seeds.

| Model | step R@1 | unit R@1 | approach R@1 / R@5 | intent R@1 / R@5 | LM loss |
|---|---|---|---|---|---|
| Qwen2.5-Coder-0.5B, plain fine-tune (E1) | 0.06 | 0.06 | 0.05 / 0.23 | 0.05 / 0.18 | 0.805 |
| **tree** | 0.18 | 0.15 | 0.14 / 0.50 | 0.07 / 0.34 | 0.799 |
| **free** | 0.30 | 0.26 | 0.48 / 0.99 | 0.24 / 0.78 | 0.804 |

Controls show that these gains come from pairing each description with its own span. Shuffled descriptions erase
them; the same text without span grounding gives no step/unit gain.

## Caveats

- Trained only on **CodeContests** (competitive programming, stdin/stdout). KodCode/TACO-style or production code is untested.
- **Intent** is the weakest level: part of a task description is not in the code at all.
- Most programs (63–74%) have **one function**, so unit and program often cover the same lines.
- Unit vectors are less spread out than the other levels (lower effective rank).
- One seed per variant is released; seeds 23 and 37 exist and can be exported the same way
  (`scripts/export_release.py`).
- Validation numbers only; a held-out test-split evaluation is pending.

Each folder's `metadata.json` holds the source run and its final validation metrics. `scripts/verify_release.py
--model <folder>` re-checks that a folder reproduces them (both do, exactly).
